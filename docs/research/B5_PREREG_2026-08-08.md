### What B4 v1 taught, and what changed because of it

1. **The winner snapshot was keyed on the wrong metric.** `best.pt` was
   selected on the raw in-training `clear_rate`, which near-flag rung
   restarts inflate, so it landed at **iter 80 — mid-ladder, before the
   cursor ever reached the entrance** — and cold-scored 0.02 greedy.
   *Fixed code-side (a580f99):* in backward mode the winner is keyed on the
   `TauScheduler` trailing success window and only once the cursor is
   at-entrance (at tau 0 the trailing window **is** entrance performance).
   Pre-entrance nets are never retained as the deliverable. No config key —
   unconditional for backward runs.
2. **Entropy collapsed 0.19 -> 0.04 after ~iter 130.** The mid-ladder
   policy actually travels 1-1 better than the baseline under sticky
   (greedy episodes reach gx 3154-3157), but the collapsed **argmax refuses
   the final flag jump the sampled policy still takes**: greedy 0.02 vs
   sampled 0.50 / 0.63. Ten pixels short of the pole is not an exploration
   failure, it is a sharpening failure.
   *Fixed config-side (this attempt):*
   `backward_curriculum.entropy_guard: {floor: 0.08, boost: 3.0}` — opt-in,
   see §6.
3. **The tau ladder walks faster than the run needs.** Measured on B4 v2:
   19.3 s/iter at 60 envs (3.2-3.5k env-steps/s), full 757-rung ladder in
   ~115 iters. That is the number §3 budgets against. *(Observed live

   advances=19  AT-ENTRANCE` at **iter 87** — 4.6 iters/advance, and
   19.27 s/iter. Every budget below uses the slower 6.05 figure and is

**The 1-2 ladder is ~60% longer than 1-1's** (1,214 vs 757 rungs, 31 vs 19

**The gauntlet, located on this tape.** The CGSA-registered hard core of
1-2 is global-x 1600-2200 in area 2 (`trainer.CGSA_GAUNTLET_GX`). On the

* **gauntlet tail: tape step 627** (gx 2199) — the cursor, walking
  backward, reaches this first;
* **gauntlet head: tape step 440** (gx 1600) — the cursor is *past* the
  gauntlet once tau <= 440. With 40-entry advances from 1214, tau lands on
  454 after 19 advances and **414 after 20**, so "past the head" is

At B4 v2's measured pace (6.05 iters/advance) 20 advances is ~121 iters and
the full 31-advance ladder is ~188 iters. Both budgets below are ~2.4x that.

## 3. The exact run

Two seeds, each its own **attended** ~2.5 h window (no overnight compute).
Seed 0 first; seed 1 only after seed 0's window closes.

```
.venv/bin/python scripts/train_game.py \
    --profile configs/mario_1_2_backward.yaml \
    --rom "roms/Super Mario Bros. (World).nes" \
    --iters 450 --num-envs 60 --seed 0 --no-resume --strict-config
```

(then the identical command with `--seed 1`.)

* **Why 450.** 2.5 h = 9,000 s; at the measured 19.3 s/iter that is 466
  iters, rounded down to 450.
* **The one caveat, registered up front.** 19.3 s/iter was measured on
  **1-1 at `rollout_steps: 1024`**. This profile runs `rollout_steps: 1536`
  (1.5x), which the config header already expects to cost ~20 s/iter and
  which could plausibly cost up to ~29 s/iter. **The window is time-boxed,
  not iteration-boxed:** the run stops at whichever comes first, iter 450 or
  the 2.5 h wall. `--iters 450` is a ceiling, not a target, and falling
  short of it is not a failure of the hypothesis — it is reported as the
  iteration count actually reached.
* **s/iter is recorded from the first 20 iters** (`[vanilla_ppo] iter N
  throughput:` lines) before anything else is read, so the whole run is
  interpreted against a measured pace rather than an assumed one.
* `--iters` is supplied on the CLI only; the profile carries no iteration
  count and must not acquire one.
* `--strict-config` is mandatory: it rejects unregistered `reinforce` keys,
  which is this project's dead-knob bug class. (Verified 2026-08-08: this
  profile passes strict validation with the `entropy_guard` block in place.)
* Checkpoints land in `checkpoints/mario_1_2_backward/` every 10 iters as
  `vanilla_ppo_iter_00NNN.pt`; the retained winner is
  `checkpoints/mario_1_2_backward/winners/best.pt`. `vanilla_ppo_iter_*.pt`
  files are **not** rotated, so the interim checkpoint survives to be
  probed after the run.

## 4. Interim probe (read at ~iter 300)

The segment probe asks the only question that distinguishes "the cursor
walked back" from "the policy can traverse": from a banked rung at gx 1600,
under the honest noise model, how often does it reach gx 2200?

```

    --profile configs/mario_1_2_backward.yaml \
    --checkpoint checkpoints/mario_1_2_backward/vanilla_ppo_iter_00300.pt \
    --bank checkpoints/backward_states/1-2 \
    --from-gx 1600 --to-gx 2200 \
    --episodes 30 --sticky-prob 0.25 --start-jitter 16 \
    --eval-seed 0 --action-select greedy
```

and the same command with `--action-select sampled`. Both are reported.

* No `--from-area` is needed: the minted bank's `index.json` is
  authoritative and the default resolves 1-2's underground main area
  (1,099 of the 1,215 entries), not the 116-step overworld stub.
* **Which checkpoint.** iter 300 if the window reached it; otherwise the
  checkpoint nearest the **2/3 mark of the iterations actually completed**.
  Registered now so the choice is not made after seeing the log.
* Direct comparison: the published B3/S3 control is 0/30 on this same
  segment (`RESULTS_1_2_HONEST_PROTOCOL_2026-07-24.md`).

## 5. The two-tier gate

**Tier 1 — INTERIM (read at ~iter 300, before the window closes).**
The cursor has walked **past the gauntlet head** — tau <= 440 (gx 1600),
i.e. at least 20 advances — **with a trailing rate >= 0.20 at the
then-current rung**, read off the per-iter `[backward]` line
(`trailing S/N=R`). Both halves are required: tau past the head with a
stalled sub-threshold trailing rate means the cursor arrived and stopped,
which is not a pass.

**Tier 2 — HEADLINE (the claim).**
**>= 1/30 cold-entrance clears at sticky 0.25 + jitter-16.** One clear in
thirty, from the true 1-2 entrance, under the honest protocol, would be the
**first ever recorded under this protocol** — the standing prior is 0/400
(Dossier v3) and 0/30 per seed (the published negative).

The headline eval:

```
.venv/bin/python scripts/eval_game.py --game mario \
    --profile configs/mario_1_2_backward.yaml \
    --checkpoint checkpoints/mario_1_2_backward/winners/best.pt \
    --start-state runs/live_show/smb_4_4_micro/entrance_after_1-1.state \
    --episodes 30 --sticky-prob 0.25 --start-jitter 16 \
    --eval-seed 0 --action-select greedy
```

run for `--action-select {greedy,sampled}` x `--eval-seed {0,1}` x both
training seeds. `--game mario` names the ROM/profile registry key;
`mario_1_2_backward` is not a registry key and exits `no_rom`.

**Reading the tiers honestly.**

* Tier 2 met (>= 1/30, warp_rate 0, on both seeds) = **first non-zero under
  the honest protocol.** That is the claim, and it is *not* "1-2 solved."
* The config header's `GATE B5` (cold-greedy **>= 0.30**, warp_rate 0, both
  seeds) is unchanged and is the bar for **solved**. Between 1/30 and 0.30
  the result is MARGINAL and is reported as "first non-zero, not a solve",
  not rounded up.
* Tier 1 met + Tier 2 missed = the curriculum walks but does not compose:
  the policy learns rungs it cannot chain. That is a real, reportable
  negative about reverse curricula on this level, and it is the exact
  failure the welded-CGSA run could not see.
* Tier 1 missed = the curriculum did not get far enough to test anything;
  report the pace, do not report a 1-2 verdict.
* **`warp_rate == 0.0` is a precondition on every clear number.** The 1-2
  pipe warp is not a clear.

## 6. The entropy guard (new, opt-in, and what would falsify it)

`configs/mario_1_2_backward.yaml`:

```yaml
  backward_curriculum:
    entropy_guard:
      floor: 0.08
      boost: 3.0
```

Arms when the **10-iter trailing mean** policy entropy falls below 0.08,
multiplies `entropy_coef` by 3.0 while armed, and disarms once the trailing
mean recovers above 0.10 (floor x 1.25 hysteresis). Floor 0.08 sits between
B4's healthy plateau (~0.19) and its collapse (~0.04), nearer the collapse,
so a merely-consolidating policy is left alone. Arm and disarm emit
`[backward-guard]` lines; the armed fraction over the last 50 iters rides
the per-iter `[backward]` line.

It is **opt-in and absent everywhere else** — with the block absent the
loop is byte-identical, which is what keeps B1-B4's lineages comparable.
It composes with the existing `entropy_floor: 0.02` controller rather than
racing it: the guard strips its own multiplier before that controller reads
the coefficient, so the boost never compounds and never contaminates the
base; while armed the effective ceiling is `entropy_coef_max x boost` =
0.15, deliberately, because `entropy_coef_max` bounds the steady state and
not the emergency.

**This is an intervention, so it carries its own falsification:** if the
guard arms and the run's cold-entrance greedy still trails its own sampled
number by the B4 v1 margin (0.02 vs 0.50), the guard did not address the
mechanism and the argmax pathology is not an entropy problem.

## 7. Kill criteria (stop the run; do not "give it more iters")

Registered in advance, each readable from the run log alone:

1. **Tau stall.** The cursor sits at **one rung for 150 consecutive iters**.
   At B4 v2's measured 6.05 iters/advance that is 25x the expected dwell;
   the rung is not learnable at this window/threshold and more iters buy
   nothing.
2. **Guard saturation.** The entropy guard is **armed for more than 50% of
   any 50 consecutive iters** (read directly off the `armed N/50` field on
   the `[backward]` line). A guard that is permanently on is no longer a
   guard — it is an undeclared change to `entropy_coef`, and the run is no
   longer testing the registered configuration.
3. **Argmax pathology (the B4 v1 signature).** At any interim checkpoint, a
   **10-episode sampled-vs-greedy spot probe** from the cold entrance:

   ```
   .venv/bin/python scripts/eval_game.py --game mario \
       --profile configs/mario_1_2_backward.yaml \
       --checkpoint <interim ckpt> \
       --start-state runs/live_show/smb_4_4_micro/entrance_after_1-1.state \
       --episodes 10 --sticky-prob 0.25 --start-jitter 16 \
       --eval-seed 0 --action-select {greedy,sampled}
   ```

   If sampled clears and greedy does not (the 0.50-vs-0.02 shape), stop and
   diagnose the collapse rather than spending the rest of the window on a
   policy whose deliverable is already known to be the wrong artifact.
   **10 episodes is a spot probe, not a gate** — it can only trigger a
   diagnosis, it can never support a claim (see §8).

## 8. Honest-reporting clause

Binding on every number this attempt produces:

* **Greedy AND sampled are both reported, always**, side by side. A greedy
  number published without its sampled twin (or vice versa) is not a
  result. B4 v1 is the reason: 0.02 and 0.50 are the same policy.
* **Both seeds complete before any claim is made.** A single-seed number is
  an observation, not a finding.
* **Every clear number carries `warp_rate`** and is void unless it is 0.0.
* **>= 30 episodes for anything called a gate.** Three-episode gates are
  known mirages on this project (one hid a true success rate under 1/400);
  the 10-episode probe in §7.3 exists only to trigger a diagnosis.
* **Cold start, always** — from
  `runs/live_show/smb_4_4_micro/entrance_after_1-1.state`, the tape's own
  root, with no test-time state loads. The tape and the entrance are one
  lineage; a mismatched pair silently evaluates a two-lineage mixture.
* **The CGSA-era 0/400 prior was measured on a different 1-2 entrance** and
  is a prior, not a paired control. The paired control is B3's 0/30 on this
  segment.
* If the run is stopped by a kill criterion, **the kill is reported** with
  the iteration it fired at. A run that ends early is a result.

*Terminology addendum, 2026-08-11.* "The argmax tie at the flagpole"

CONFIDENT-WRONG NOOP SHARPENING — margins rise 14x across the entropy

rungs. It is not a tie in the sense of two options scoring equally; the
policy becomes confidently wrong. The phrase is left as originally
written above (this is a naming correction, not a re-run), and readers
citing "argmax tie" from this point forward should cite noop-mode
sharpening instead.

## Addendum 3 + RUN VERDICT (2026-08-09, registered stall criterion fired)

Run 2 stopped at iter 266 by the PRE-REGISTERED kill criterion (tau
stalled 156 iters at rung 893, gx 2674). Root cause, receipted from
telemetry: TRUNCATION-STARVED ADVANCE WINDOW — episodes from the rung
neither die nor complete within budget (truncated 15,914; trailing
0/0 = zero SCORED attempts across the entire stall), so the advance
gate can never fire. This is precisely the length-biased-truncation
defect the adversarial review flagged at implementation time (as a
MAJOR) and it is now empirically confirmed as run-blocking at 1-2
scale.

**Classification: MECHANISM-INCOMPLETE, not a capability negative.**
The wall was not tested — tau never reached the gauntlet (gx 1600-
2200); no cold-entrance episode was gated. G2's pass/fail branches
assumed a capability verdict; adjudicating "learning demoted" on a
scoring-semantics defect would be dishonest in the opposite direction.
Equally: the strategy's "B5 runs once" stop forbids silently cycling
into run 3. DISPOSITION: runs halt here; the two receipted mechanism
repairs (truncation counted as window failure OR per-rung episode
budget; both one-change fixes) go to the owner with this verdict, and
any run 3 is the owner's call, not the loop's.

For the record, what the machinery DID prove on 1-2 today: tau walked
1093 -> 893 (5 advances through the flag zone at >=0.20 trailing) —
