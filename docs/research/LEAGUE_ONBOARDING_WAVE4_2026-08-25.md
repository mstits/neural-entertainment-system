# League Onboarding — Wave 4 (2026-08-25)

Eight fresh candidates (never touched by waves 1-3, no start state minted), surveyed against all prior wave receipts and the ROM library, then minted + odometer-gated + classified with a `--workers 4 --minutes 2` smoke.

## The headline finding: the ASM-CPU NMI-batching bug reproduces on a second game

The Journey to Silius attempt hit a real INSTRUMENT bug, not a game finding: the default `Pool` (`disable_asm_cpu=False`, the engine's live default per `nes_core/src/pool.rs`'s own comment "Off by default (asm_cpu stays on, matches GUI / single-env)") produced an identical flat trace (range x=0) under every held direction. Cross-checked against `nes_core.NESEnvironment` (interpreter-only) and rendered frames: real scroll growth exists (odo_x 0→783 under held RIGHT, confirmed visually — scrolling skyline, displaced sprite, populated HUD). This is the same PPU/NMI-batching defect on record in project memory for SMB (`project_asm_cpu_disabled_2026-04-26.md`, "ASM CPU disabled — Mario walks").

Direct code inspection (`nes_core/src/nes.rs:269`, `disable_asm_cpu: false` is the struct default; `nes_core/src/pool.rs:1288`'s own comment; zero call sites for `set_disable_asm_cpu` anywhere in `src/emulation/`, `src/training/`, or `scripts/train_game.py`) found no mechanism in the live training/onboarding pipeline that disables the ASM CPU by default — including for Mario. The commit the stale project memory cited for "default builds skip ASM CPU" (`6a4304d`) does not exist in this repository's history; `Makefile`'s `build` target has compiled `asm_cpu` in unconditionally since this repo's first commit.

**Addendum, same day — de-escalated via direct empirical retest, do not read the paragraph above as casting doubt on SMB/v27/v28.** Re-ran the project's own `nes_core/tests/asm_vs_slow_smb.rs` and `asm_vs_slow_mmc1.rs` lockstep diagnostics against current HEAD with `--features asm_cpu`: **both pass clean — "No divergence in 1500000 instructions"** for SMB and for the MMC1 golden ROM (Castlevania II). v27/v28's SMB training is not called into question — it is the exact game this lockstep test re-verifies clean today. What remains open and narrower: Journey to Silius's specific flat-trace anomaly is not yet lockstep-confirmed as a real ASM/interpreter divergence (only compared against itself with the flag toggled) — could be a genuine per-ROM gap the existing golden tests don't cover, or an unrelated misdiagnosis; needs the standard nes-py/Mesen oracle protocol, not urgent. The build-config drift itself (Makefile compiling in a feature an old memory says should default off) is a separate, real, low-urgency loose end worth a deliberate decision rather than silent drift. Full detail in the corrected `project_asm_cpu_disabled_2026-04-26` memory.

The workaround used to get a trustworthy Journey to Silius reading (`pool.set_disable_asm_cpu(True)` patched in via a throwaway driver script) was NOT applied anywhere in the repo — it lives only in this session's scratchpad.

## Synthesis

**5 of 8 landed SOUND_ADVANCING** (Super C, DuckTales 2, Darkwing Duck, Journey to Silius, Ninja Gaiden II). **1 is SOUND_GAME_STOPS** with a named, unconfirmed lead (Mega Man's possible lives-byte underflow). **2 are mint_failed** (Castlevania III, Power Blade) — both genuinely never became interactive within a generous probe budget, not misdiagnosed instrument faults; both correctly left no start state or config behind (Power Blade's low-confidence candidate state was actively deleted rather than banked for a later stage to pick up by accident).

**Discipline that held up this wave:**
- Two false-positive mints were caught by rendered-frame VISUAL checks before being trusted (DuckTales 2's animated world-map select screen, Darkwing Duck's static story-briefing screen) — the input-divergence RAM heuristic alone would have banked both as "live."
- The ASM-CPU bug was root-caused, not worked around silently or misreported as a game-specific wall (which would have produced a false CAMERA_STATIC_AGENT_ACTIVE or SOUND_GAME_STOPS verdict for Journey to Silius).
- Mint failures were confirmed with two independent probe designs (a short boot-mash AND a long extended trace) before being called, ruling out "just needs more time past a slow intro" as an explanation.
