## Trigger condition — read this before spending anything

**This document is a design, not a launch order.** It fires only if the
actual v27 verdict — best-of-4 pooled honest greedy on the ReDo-on,
merged-785-rung-ladder run, scored against PASS >= 0.80 / FAIL <= 0.767
— reads **FAIL or MARGINAL**. If v27 PASSED, this experiment is moot:
do not spend the budget below speculatively, and do not retroactively
read a PASS as license to "confirm it further" with more capacity. The
scoring of v27 and the decision to launch v28 are two separate acts;
whoever reads the v27 verdict makes the launch call, not the existence
of this document.

## The registered question

v27 (merged recovery-in-curriculum ladder + mandatory ReDo, fresh net,
48.1k params) tests whether untrainability is a property of **post-hoc
consolidation** vs. **the parameter budget**. If v27 fails at 48k with
ReDo armed — i.e. with the DR's own confound (primacy bias / dormant
units) instrumented and controlled — the FAIL verdict's text says the
capacity itself is the suspect. v28 tests that reading directly: **does
the same treatment, at more parameters, do measurably better**, or does
adding capacity buy nothing?

This is deliberately *not* a re-litigation of the consolidation
question. Everything about v27's design that answered "is recovery-in-
curriculum-from-scratch better than post-hoc distillation" stays fixed.
The only thing that moves is net width.

## Single variable: `tile_hidden_dim` 64 -> 96, nothing else

`src/models/tile_policy.py`'s `TilePolicyNetwork` takes `hidden_dim`
and `trunk_dim` as ordinary constructor args, already exposed as the
schema-legal config keys `tile_hidden_dim` / `tile_trunk_dim`
(`src/training/rollout_config.py:71-72`, `config_schema.py:69`,
already used at other widths across `configs/mario_1_2_*.yaml` and the
`_online_v1` family). Both `TilePolicyNetwork` and the `redo.py`
mechanism read every shape off the live tensors
(`dormant_indices`/`hidden_activations` operate on whatever `h1`/`h2`
shape they're given; `RedoStats.hidden_dim = int(h1.shape[1])`) — there
is **no code to change** for a wider net. This is what makes it the
smallest possible capacity experiment: a one-line config diff against
each of the four already-registered v27 seed configs, zero new trainer
machinery, zero new mechanism classes — exactly the "config-and-data
only" discipline v27's own Mechanism Decision section argued for and
that this month's void history (2-1 on the wrong ladder, Phase 3's
frozen actor, the options 1e12 sentinel) keeps punishing when skipped.

**Why `hidden_dim` alone, not `trunk_dim` too, not a third layer.**
Three capacity candidates exist against this architecture:

| Candidate | Change | Params | Code touched |
|---|---|---|---|
| **1 (chosen)** | `hidden_dim` 64->96 | 72,039 (~1.50x) | none — config only |
| 2 | `hidden_dim` 64->80, `trunk_dim` 32->40 | 60,824 (~1.26x) | none — config only |
| 3 | add `fc3` (32->32) trunk layer | ~49,300 (~1.02x) | `tile_policy.py` save/load contract, `build_tile_policy_from_checkpoint`, ARCH_VERSION bump |

Candidate 3 tests depth instead of width at near-zero extra params, but
it changes the checkpoint contract and adds a new architecture path —
two more places for a silent-mechanism void to hide, for a question
this experiment isn't asking (v28 asks "does more capacity help", not
"is it width or depth"). Candidate 2 is a real alternative (more
balanced widen) but touches two knobs where one suffices to fasten the
single-variable claim to a single number. **Candidate 1 is registered**
as the primary and only arm: biggest capacity lever per line changed,
provably zero-code-risk, and a clean plain-English claim ("we gave it
50% more parameters and changed nothing else"). Candidate 2 is named
here as the natural graduated follow-up if v28's own falsifiable
prediction (below) lands ambiguous — not run now, not budgeted now.

Exact parameter accounting (feature_dim=712, num_actions=6, both
candidates use the architecture formula
`fc1 + norm1 + fc2 + norm2 + actor + critic`):

```

candidate1(hidden=96, trunk=32): 68,448 + 192 + 3,104 + 64 + 198 + 33 = 72,039
```

`+23,904` params, `1.497x`. The live `[policy] class=TilePolicyNetwork

## Why capacity-only, not capacity+something-else

A wider net trained with the *same* learning rate, same rollout size,
same iteration budget could in principle be undertrained relative to
its larger weight space within 250 iters — that would make a FAIL at
72k ambiguous between "more capacity doesn't help" and "this capacity
needed more/different optimization to express itself." Retuning lr or
budget to compensate would fix that ambiguity but introduces a second
variable, which is exactly what "single variable versus the v27
configs" forbids. **This is a registered, honest limitation of the
design, not an oversight**: v28 tests "does capacity help under the
identical recipe", not "is there SOME recipe at 72k that clears the
bar." A capacity PASS is unambiguous evidence for the capacity
hypothesis. A capacity FAIL is evidence against capacity-under-this-
exact-recipe, and is reported as such — it does not by itself rule out
a wider net trained differently, and the writeup must say so rather
than overclaim a closed door.

## ReDo at the new width — re-validated, not assumed

The dormancy statistic (`s_i = E|h_i| / layer_mean`) is scale-invariant
in the number of units, so `tau=0.025` is expected to carry over
unchanged. What does **not** automatically carry over is the *recycle-
size* calibration from Addendum 2's tau-sweep: the soft-VOID trigger
"> 15 units recycled in one event" was measured against a 64-unit fc1 /
32-unit trunk (96 scoped units total), and its absolute value is an
artifact of that width's dormancy-score distribution — a different
width can have a different distribution. Per the standing project
lesson ("re-run the forced-recycle sweep per new trained checkpoint,
don't assume the old table transfers"), this is **re-measured, not
assumed**, exactly as Addendum 2 did for v27 itself:

**V28's own forced-recycle preflight** (V3 below): before the 4x250
spend, one throwaway copy of the seed-0 v28 profile runs 2 iters with
`redo_tau` swept over the same grid Addendum 2 used
(`{0.05, 0.08, 0.10, 0.15, 0.20, 0.25, 0.30, 0.35, 0.5}`), on the
**96-unit** net. This produces v28's own isolated-event vs. batch-
collapse boundary (Addendum 2's table, re-run) and the registered
soft-VOID trigger for the real runs is whatever that boundary turns out
to be at this width — not a naive 15 * (128/96) = 20 proportional
guess. If the new boundary differs meaningfully from 15, that
difference is itself worth one line in the writeup (it would mean
dormancy dynamics are also width-sensitive, a fact about the mechanism
independent of the capacity question). Real v28 runs launch from the
registered `tau=0.025` regardless of what the sweep finds at forced
tau values — the sweep only sets the soft pause trigger.

## Pre-registered gate — same numeric bar as v27

Identical protocol, identical thresholds, identical artifact-selection
rule. Nothing about the gate itself is a variable:

```
.venv/bin/python scripts/eval_game.py --game mario \
  --profile configs/mario_1_1_v28_seedN.yaml --checkpoint <ckpt> \
  --start-state runs/live_show/smb_4_4_micro/entrance_start.state \
  --episodes 50 --max-steps 1500 --sticky-prob 0.25 --start-jitter 16 \
  --eval-seed {0,1} --action-select {greedy,sample}
```

Per seed: evaluate the checkpoint with peak trailing entrance rate in
the `[backward]` telemetry (ties -> later iter) and the final
checkpoint; the seed's number is the better pooled greedy of the two.
The experiment's number is best-of-4.

- **PASS**: best-of-4 pooled >= **0.80**, warp_rate 0.0. Capacity was
  (at least part of) the ceiling — 48k was insufficient, 72k with the
  identical treatment clears the same bar v27 was measured against.
- **FAIL**: best-of-4 pooled <= **0.767** (the banked control). Under
  this exact recipe, 50% more parameters bought nothing at the gate.
  Does not by itself prove capacity is irrelevant at any width (see
  "capacity-only" limitation above) — see the falsifiable prediction
  below for how to read a FAIL further.
- **MARGINAL**: (0.767, 0.80) — report per-seed spread; do not relaunch
  or extend without a fresh registration.

These are the *same numbers* v27 was scored against, deliberately: v28
is asking "does the v27 bar move at 72k," not "what's a fair bar for a
bigger net."

## Mechanism reads (registered, non-gate)

The three v27 reads, repeated identically so they are directly
comparable, plus a fourth that is v28-specific:

1. **Recovery-band rung rates** — trailing-window clear rate while
   tau's window covers >= 1 recovery entry (marker frames >= 900000)
   vs. adjacent windows with none, per `[backward]` telemetry.
2. **Assay re-run on the winning artifact** (if PASS or MARGINAL):
   `scripts/recovery_assay.py`, 60 episodes — did the trainable-slice
   fraction shrink relative to the control's 3/9?
3. **Ladder telemetry vs. v27**: iters-to-entrance, rungs/100 iters,
   entrance-rate trajectory, compared seed-for-seed against v27's own
   recorded numbers for the same seed.
4. **Dormancy/recycle telemetry at the new width** — per-layer dormant
   fraction and recycle counts per iteration, cumulative recycles per
   seed, and whether recycle events cluster at recovery-band stalls the
   same way (or differently) than in the v27 (48k) runs.

Read #3, seed-paired against v27's already-scored numbers, is the input
to the falsifiable prediction below — it is what turns "PASS or FAIL"
into "why," rather than leaving a FAIL as an undifferentiated null.

## The falsifiable prediction

This is the point of the experiment, registered before any run so it
cannot be fitted after the fact:

> **Capacity-was-the-ceiling** predicts that widening the net produces
> a **measurable, direction-consistent improvement in the mechanism
> reads** relative to v27's matched numbers — specifically: in at least
> 3 of the 4 paired seeds, BOTH the recovery-band trailing rung-clear
> rate (read #1) AND the ladder-walk depth / iters-to-entrance (read
> #3) move in the improving direction versus that same seed's v27 run —
> **regardless of whether the honest gate itself clears 0.80.** This is
> the dose-response signature: more parameters buy more of the
> treatment's effect, even if 72k isn't (yet) enough to cross the bar.
>
> **Still-isolated-optimum / not-actually-capacity** predicts the
> opposite: mechanism reads that are flat, mixed with no consistent
> direction across seeds, or worse than v27's, despite the +23,904
> parameters and an identical treatment. This would mean 50% more
> capacity bought nothing measurable *anywhere in the run*, not just at
> the final gate — evidence that the FAIL sits somewhere the parameter
> count doesn't reach (the interleave's transient-exposure limitation
> the parent v27 doc already named as its own live counterpoint, or a
> curriculum-shape ceiling capacity does not touch), and redirects the
> next fork toward a genuinely different variable (a persistent-mixing
> recovery pool, or a curriculum reshape) rather than toward more
> width.

Reading rule, made concrete so it doesn't get eyeballed after the fact:

| Honest gate | Mechanism reads (dose-response, read #3 vs. v27) | Verdict text |
|---|---|---|
| PASS | (moot — gate already confirms capacity mattered) | Hypothesis B (parameter budget) CONFIRMED at 72k; report dose-response reads anyway for the v29 sizing question |
| FAIL/MARGINAL | improving, >=3/4 seeds | Capacity is a *real, partial* lever — 72k under-shot but the direction supports "still capacity-constrained." Names the next data point (Candidate 2 or a further width step) as the natural v29, not a foregone conclusion |
| FAIL/MARGINAL | flat/mixed/worse | Capacity, at least at this width and under this exact recipe, is not the explanatory variable. Redirects the fork to mechanism/curriculum-shape, not width |

## VOID conditions

A VOID is "the experiment never happened"; no verdict may be read.

- **V1 — single-variable diff check.** Machine diff of all four
  `configs/mario_1_1_v28_seed{N}.yaml` against
  `configs/mario_1_1_v27_seed{N}.yaml`: VOID if any key other than
  `name`, `description`, `tile_hidden_dim`, `tile_trunk_dim` (written
  explicitly, unchanged value) differs. This is the check that makes
  "single variable" a verified claim rather than an assertion.
- **V2 — parameter-count receipt.** The seed-0 startup log must print
  `[policy] class=TilePolicyNetwork params=72039 (hidden=96,
  trunk/gru=32, features=712, actions=6)` exactly. Any other number —
  a stray `tile_hidden_dim` typo, a `trunk_dim` drift, wrong
  `feature_dim` from an encoder mismatch — VOIDs before the 4-seed
  spend; do not "close enough" this number.
- **V3 — ReDo forced-recycle preflight at the new width.** The
  Addendum-2-style tau-sweep (grid above) on a throwaway seed-0 v28
  profile must show at least one tau value producing >= 1 recycle with
  finite (non-NaN/Inf) `max_dlogit`, mirroring V7's conditions (a) and
  (b-i). VOID if no tau in the grid produces a recycle (the net is
  behaving so differently at this width that the whole mechanism needs
  re-derivation before spending budget, not just a trigger number).
  The sweep's own isolated-event/batch-collapse boundary becomes the
  registered soft-VOID pause trigger for real runs (replacing the naive
  "15" from v27, per width).
- **V4 — mechanism-armed-but-inert (redo).** Reuse
  `scripts/experiment_preflight.py`'s existing `redo` entry unchanged
  (`profile_path: reinforce.redo_enabled`, `armed: r"\[redo\] ENABLED
  tau=0\.025"`, `forbidden: r"\[redo\] disabled"`) — it is already
  width-agnostic (no width-specific regex). VOID on the same terms as
  v27's V2/V4.
- **V5 — wrong-ladder guard.** Any seed whose `[backward] ENABLED`
  line does not name `checkpoints/backward_states/1-1-v27` with the
  full 785-entry count is VOID for that seed (the same class that
  voided 2-1 attempt 1: trained on the wrong ladder).
- **V6 — ladder liveness, per seed.** A seed whose tau has advanced 0
  rungs by iter 150 is VOID-machinery for that seed (S1 of the parent
  recipe, reused). If all four seeds void this way the experiment is
  VOID, not FAIL.
- **V7 — eval lineage.** Any gate eval not run with `--start-state
  runs/live_show/smb_4_4_micro/entrance_start.state` and the registered
  flags is discarded, not reported.
- **V8 — checkpoint-shape sanity for the paired mechanism reads.** Read
  #3 requires diffing v28's per-seed ladder telemetry against v27's.
  VOID that specific read (not the whole experiment) for any seed pair
  where the v27 log used to compare against cannot be located or is
  itself flagged VOID in the v27 writeup — do not silently compare
  against a number that was never a real verdict.

### Why this row and not the other one — the honest reading of the count

The count is 3/4, but it is a 3/4 with real load-bearing caveats, and
the case for the other row is not empty:

1. **Read #3 has a sub-metric the prediction does not name, and it is
   ambiguous.** The mechanism-reads section defines read #3 as three
   things (iters-to-entrance, rungs/100 iters, entrance-rate
   trajectory); the *prediction* names only "ladder-walk depth /
   iters-to-entrance." The trajectory sub-metric was computed anyway,
   and it is where the ambiguity lives: the authoritative per-run peak
   entrance rate is ceiling-saturated in all 8 runs (0.867–1.000,
   ±0.09 SE off a 30-episode window) and reads "flat" in 3 of 4 pairs.
   Requiring that saturated metric to also move drops the count from
   **3/4 to 1/4** (only seed 0 survives unhedged). The lower-variance
   members of the same family — mean entrance-era rate and fraction of
   iterations at ≥0.50 — agree with each other and with the named
   metric in every seed. The adjudication here follows the prediction's
   own wording (which names iters-to-entrance / ladder-walk depth, and
   under which the count is 3/4 either way), but the alternative
   reading is recorded rather than buried, because it would flip the
   selected row.
2. **Reads #1 and #3 are not two independent votes.** Both are
   downstream of the same thing — how readily the policy clears rungs.
   Higher recovery-band clear rates mechanically shorten the walk to
   the entrance. The registered conjunction reads as two confirmations
   but is closer to one signal measured twice, which weakens the
   dose-response evidence below what "BOTH reads agree" sounds like.
3. **Seed 2's read #1 delta is inside the noise** (−0.0019 on N≈360–540
   trailing attempts). Calling it "flat" rather than "worse" does not
   rescue the conjunction for that seed — the prediction requires
   *improving*, and flat is not improving — so the count is 3/4 under
   either treatment. But the honest description of seed 2's read #1 is
   "no measurable change," not "degraded."
4. **The "recovery bands are harder" premise is partly a depth
   confound.** Against the global non-recovery comparator, recovery
   bands look far harder in all 8 runs (e.g. 0.064 vs 0.333). Against a
   local-adjacent comparator (only the tau checkpoints immediately
   flanking each recovery band), the gap shrinks sharply and reverses
   in 2 of 8 runs. This does not touch the v27-vs-v28 count — that is
   driven entirely by the recovery-band numerator, identical under
   either comparator — but it means "recovery rungs are intrinsically
   harder" is a weaker claim than the global numbers suggest.
5. **The gate still FAILed.** This row is a direction-of-travel
   verdict sitting underneath a failed gate. It is not a partial pass,
   and 0.670 is not "nearly 0.80."

### Seed-paired gate comparison vs. v27 (48k → 72k)

Same protocol, same selection rule, same 785-rung ladder, same ReDo
treatment — only the width differs:

| seed | v27 peak | v27 final | v27 seed best | v28 peak | v28 final | v28 seed best | gate Δ |
|---|---|---|---|---|---|---|---|
| 0 | 0.040 | 0.020 | 0.040 | 0.450 | 0.000 | 0.450 | **+0.410** |
| 1 | 0.290 | 0.020 | 0.290 | 0.230 | 0.050 | 0.230 | −0.060 |
| 2 | 0.530 | 0.000 | 0.530 | 0.370 | 0.000 | 0.370 | −0.160 |
| 3 | 0.170 | 0.010 | 0.170 | 0.670 | 0.000 | 0.670 | **+0.500** |
| **best-of-4** | | | **0.530** | | | **0.670** | **+0.140** |

Two things are true at once here and neither is allowed to swallow the
other. **The headline moved: best-of-4 0.530 → 0.670, a real +0.14 at
the gate**, measured under an identical protocol on 100 pooled episodes
per checkpoint — that is not noise and it is not nothing. **And the
per-seed deltas are genuinely MIXED**: two large gains (+0.410, +0.500)
and two moderate regressions (−0.060, −0.160). The best-of-4 statistic
takes the max over seeds, so it is structurally biased toward reporting
improvement whenever *any* seed improves; a 2-up/2-down seed field that
raises the max is exactly the shape that best-of-4 flatters. The
registration chose best-of-4 deliberately (it is "the same selection
freedom the banked 0.76 had"), so it is the registered number and it
stands — but the per-seed spread is the honest picture of what 24k
extra parameters bought: **higher variance across seeds, with the
upside larger than the downside, not a uniform lift.** Notably, the two
seeds that improved at the gate are also two of the three that improved
on both mechanism reads, and the seed that regressed most at the gate
(seed 2, −0.160) is the same seed that regressed on both reads —
seed-level coherence between the gate and the mechanism reads, which
is a point in favor of the dose-response story even though the gate
failed.

### Secondary finding: peak instability reproduces a THIRD time, and more starkly than ever

Every single v28 seed's final iter-240 checkpoint scored at or near
zero against a substantially non-zero peak:

| seed | peak pooled | final pooled | collapse |
|---|---|---|---|
| 0 | 0.450 | 0.000 | −100% |
| 1 | 0.230 | 0.050 | −78% |
| 2 | 0.370 | 0.000 | −100% |
| 3 | 0.670 | 0.000 | −100% |

Three of four seeds collapsed to **exactly 0.000 over 100 pooled
episodes** — not a degradation, an erasure. This is the third
independent reproduction of the pattern: first on post-hoc continued
PPO (−74% over 200 iters), then within v27's from-scratch runs
(0.04→0.02, 0.29→0.02, 0.53→0.00, 0.17→0.01), and now at 72k on a
wider net that never saw a post-hoc gradient either. It is also the
starkest instance yet in absolute terms — v27's peaks were low enough
that the collapse destroyed little; v28 destroyed a 0.670 artifact.

Adding capacity did **not** mitigate it. If anything the taller peaks
made the fall further. **Preserve-on-peak (`winners/best.pt`) is again
the only reason this experiment has a number at all**: scored on final
checkpoints alone, v28's best-of-4 would be **0.050**, not 0.670. This
is now a property of the architecture/recipe class demonstrated across
two parameter budgets, two delivery mechanisms, and three campaigns —
preserve-on-peak stays mandatory in every arm of this line, and any
future registration that scores only a final checkpoint is
mis-specified.

### Secondary finding: ReDo was armed, correct, and completely inert — at BOTH widths

Read #4's finding is unambiguous and it matters for how v27's own
verdict should be read. Across all 2,000 per-iteration checks (8 runs ×
250 iters, `check_every_iters=1`, zero skipped iterations, zero
`[redo] disabled` lines), the logged dormant-unit count was **`0/64`
and `0/32` on every v27 iteration and `0/96` and `0/32` on every v28
iteration**. Cumulative recycles: **0 for all eight runs.** Per-layer
dormant fraction, max and mean, for both layers, in every seed at both
widths: **0.0**.

The mechanism is not broken — both experiments' forced-recycle tau
sweeps fire correctly (v28: 0 recycles at tau 0.15/0.20, 9 at 0.25, 6
then 13 at 0.30, all with finite `max_dlogit`) — the registered
`tau=0.025` simply sits far below anything real 1-1 rollouts ever
produced on a SiLU + pre-activation-LayerNorm net, at either width.
Width made **no** difference to recycle activity: identically zero.

Three consequences, stated at the strength the data supports:

- **v27's FAIL verdict text needs its registered caveat read aloud.**
  AMENDMENT 1's FAIL mapping quotes the DR's "ReDo mathematically
  guarantees that all 48k parameters were active and non-dormant." ReDo
  guaranteed nothing of the kind — it never fired. What actually holds
  is the weaker statement B2/B5 registered in advance for exactly this
  case: the dormancy confound **never materialized** on this
  architecture, so plasticity was *measured-intact by the dormancy
  statistic*, not actively maintained. The capacity verdict still
  stands, and the registration deserves credit for having written that
  caveat before the telemetry came back — but the mechanism read must
  say so explicitly, and this is it saying so.
- **ReDo cannot explain any of the mixed per-seed gate deltas.** It was
  equally and totally inert in both arms; whatever drove seed 0's
  +0.410 and seed 2's −0.160 ran through the ladder walk, the
  curriculum interaction, or capacity's direct effect on the policy —
  not through dormant-neuron recycling.
- **The soft-VOID trigger was never approached.** V7(b-iii)'s
  per-width boundary (~6 units at tau 0.30 for the 96-unit net, vs. ~2
  for v27's 64-unit net — itself a real finding: dormancy dynamics
  *are* width-sensitive, which is why re-measuring instead of scaling
  "15" proportionally was correct) never came into play, because no
  recycle event ever occurred.

### Instrumentation gaps found while adjudicating

Four, all worth fixing before the next registration in this line:

1. **The `[backward]` telemetry line is not the number the winner
   selector reads.** `winners/best.json` for v27 seed 0 records
   `entrance_trailing_rate=0.8667 @ iter 60` while that iteration's
   printed log line says `trailing 16/30=0.53`. Cause, read from
   `trainer.py`: a second `bwd_sched.record(...)` force-completion pass
   runs *after* the telemetry line prints and *before* the winner-save
   block reads the window, adding scored episodes in between. The
   log-derived peak is therefore a **lower bound** on the
   winner-selection peak. Both arms share the code path so seed-paired
   *directions* are unaffected, but any future read that treats the
   printed line as the selection metric will be wrong.
2. **No continuous dormancy-score trace exists.** `redo.py` logs only
   post-threshold counts, never the underlying `s_i` values. So "ReDo
   never fired" is established, but "how close did dormancy get to
   0.025" is unanswerable from the receipts — which is precisely the
   quantity that would tell us whether tau was mis-calibrated by a
   little or by an order of magnitude. Logging the min/median `s_i` per
   layer per check would cost nothing and close this.
3. **The V1 receipt named in the receipts layout was never written.**
   `runs/v28_capacity/config_diff.json` does not exist. V1 was
   genuinely checked pre-launch (asserted in launch commit `3fca666`)
   and its substance is verified above by re-running the diff against
   configs that git confirms are unchanged since that commit — but the
   named machine receipt was skipped. A registered receipt path that is
   never written is a gap even when the check itself was honest.
4. **`warp_rate` has no field in the eval receipt.** The PASS branch
   requires `warp_rate 0.0`; `eval_game.py`'s JSON carries
   `clear_rate`, `max_gx_per_episode`, and `max_byte_seen` but no warp
   counter. It never bound here (the gate FAILed, and every clear shows
   `max_gx` at the 3161 flagpole with `max_byte_seen: 0`), but a future
   PASS in this family could not be scored against its own registered
   condition as written.
